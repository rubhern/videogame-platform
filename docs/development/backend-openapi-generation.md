# Backend OpenAPI generation

- **Status:** Mandatory backend HTTP standard
- **Source contract:** [`docs/architecture/api/openapi.yaml`](../architecture/api/openapi.yaml)
- **OpenAPI:** `3.1.2`
- **Generator:** OpenAPI Generator Maven Plugin `7.24.0`
- **Backend:** Java 25, Spring Boot 4.1.x, Jakarta, and Jackson 3

## Purpose

The reviewed OpenAPI document is the source of truth for every product-facing
backend HTTP API. Maven generates the Spring operation interfaces and transport
models before Java compilation, so an incompatible controller signature or mapping
fails the normal build.

```text
docs/architecture/api/openapi.yaml
    -> openapi-generator-maven-plugin
    -> target/generated-sources/openapi/java
    -> manual api.delivery adapter
    -> application use case
    -> domain
```

Generation does not create business logic or an editable controller implementation.
Generated Java is disposable build output under `backend/target/`, is ignored by Git,
must not be edited, and is regenerated by every clean Maven build.

## Maven lifecycle

The backend-owned execution is configured in [`backend/pom.xml`](../../backend/pom.xml)
and runs in `generate-sources`. The exact plugin version is centralized in the root
Maven property `openapi-generator.version`; it is never a floating version.

```bash
./mvnw -pl backend clean generate-sources
./mvnw -pl backend clean compile
./mvnw clean verify
```

The first command is useful for inspection. `clean compile` proves that every
generated interface and model compiles, including operations that have not yet
received a manual adapter. `clean verify` is the authoritative reproducible gate.

The configuration generates APIs and models but no generated tests,
documentation, supporting application, or controller implementation. Its relevant
options are:

| Option | Value | Reason |
|---|---:|---|
| `generatorName` | `spring` | Match the approved Spring MVC backend |
| `interfaceOnly` | `true` | Generate HTTP contracts, not controller logic |
| `skipDefaultInterface` | `true` | Require manual adapters to implement every selected operation |
| `useSpringBoot4` | `true` | Generate Spring Boot 4 and Jakarta-compatible code |
| `useJackson3` | `true` | Generate Jackson 3-specific databind imports where required |
| `useTags` | `true` | Define focused interfaces that match manual delivery adapters |
| `useOneOfInterfaces` | `true` | Preserve closed polymorphic response shapes |
| `useSpringBuiltInValidation` | `true` | Use Spring MVC's built-in method validation path |
| `hideGenerationTimestamp` | `true` | Keep regenerated source deterministic across clean builds |
| `openApiNullable` | `false` | Avoid an unnecessary nullable wrapper dependency |
| `schemaMappings: null` | `java.lang.Void` | Work around the generator's missing `ModelNull` output for required JSON-null fields |

OpenAPI Generator `7.24.0` still labels OpenAPI 3.1 support beta. Constants inside
generated polymorphic models are therefore expressed as anchored exact patterns, and
boolean invariants use JSON Schema `not`, because direct `const` produces invalid Java
enum constructors. These response-only unions omit explicit discriminator objects:
combining a discriminator with the required constant enum produces incompatible Java
accessor types in the generated `oneOf` interface. Each variant still requires its
exact distinguishing property, and Redocly validates the closed union as OpenAPI
3.1.2 JSON Schema.

Generated sources currently use Jakarta validation and annotation imports. The
generator also emits deprecated Spring `Nullable` annotations; these warnings are
accepted in disposable output and must not be silenced by editing generated files.

## Manual delivery adapters

Manual controllers remain in `com.videogameplatform.api.delivery`. Each controller:

1. implements the focused generated API interface;
2. maps generated request values to provider-independent application input;
3. invokes an application use case;
4. maps application results to generated response models;
5. constructs HTTP headers and responses;
6. translates failures to the generated `Problem` model.

`ReleaseController implements ReleasesApi` is the first executable example. The
generated base operation path is combined with the manual `/api/v1` class mapping.
Generated types are allowed only in generated code and the inbound delivery adapter.
Application, domain, catalogue, ratings, persistence, identity, and provider code
must not depend on `com.videogameplatform.api.generated`; ArchUnit enforces this
direction.

The generated API tag is an implementation grouping boundary. Give a new operation a
focused tag whose generated interface can be implemented coherently by one manual
adapter. Do not place an implemented operation in a broad interface that would force
the controller to expose placeholder methods.

## Adding or changing a backend API

1. Change and review `docs/architecture/api/openapi.yaml` first.
2. Assess the OpenAPI contract version under the Semantic Versioning policy.
3. Regenerate and inspect the interface, DTOs, Jakarta imports, Jackson imports,
   polymorphic types, nullability, and parameter defaults.
4. Implement or update the manual `api.delivery` adapter and mappings.
5. Keep application and domain signatures free of generated types.
6. Update the tracked Postman collection, requests, and assertions in the same change.
7. Regenerate the frontend types and committed readable OpenAPI reference.
8. Add behavioural, contract, and architecture tests.
9. Apply the delivery lifecycle's risk-based validation policy to the affected
   OpenAPI consumers. Run contract generation/validation and the relevant backend or
   frontend checks locally; rely on the applicable pull-request gates and the full
   trusted-`main` sequence unless a concrete cross-boundary risk justifies broader
   local validation.

If generated code does not compile, stop and resolve the contract or the smallest
documented generator compatibility option. Never patch `target/generated-sources`,
copy generated Java into `src/main/java`, generate business logic, or commit generated
Java as a workaround.

## Upgrading the generator

Review the official [Spring generator options](https://openapi-generator.tech/docs/generators/spring/)
and [release notes](https://github.com/OpenAPITools/openapi-generator/releases), then:

1. update the exact root Maven property;
2. generate from a clean `target`;
3. inspect all generated interfaces and representative models;
4. confirm Jakarta, Spring Boot 4, Jackson 3, `oneOf`, and null mappings;
5. compile and run the full test suite;
6. document any new non-default option or removed workaround.

An upgrade is a reviewed tooling change even when the public HTTP contract does not
change.

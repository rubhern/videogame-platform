VideoGame Platform Learning MVP API (3.17.0)

Download OpenAPI specification:

Browser-facing API for the approved learning MVP vertical slice.

Provider-independent, same-origin contract for release discovery, weekly and monthly featured releases, bounded-catalogue search, public game details, BFF session discovery, the authenticated user's ratings, and the catalogue operator's synchronization status, coverage, bounded synchronization request and the stop or abandonment of one run. It contains only the fifteen approved method/path operations.

Authentication navigation under /auth and the management-port synchronization, repair and localization commands are separate BFF and operational boundaries and are intentionally not exposed here. Provider image binaries are loaded from an approved CDN reference or replaced by a product-owned fallback; this API does not copy, proxy, or redistribute them.

Releases

Public recent and upcoming release discovery.

Browse recent or upcoming releases grouped by game

Reads a bounded page of games from the last valid local catalogue publication. Each game appears once with only the releases that match the requested view and active filters, presenting at most one of them per platform (see ReleaseItem); page.totalItems counts games, not releases. Platform and region filters are multi-select: values within one dimension combine with OR and the two dimensions combine with AND. availableFilters is contextual and faceted: platform options reflect the current view/window and the active region selection (never restricted by the active platform set), region options reflect the current view/window and the active platform selection (never restricted by the active region set), and a currently selected valid value always stays representable. The application derives the evaluation date and the selected bounded week window in Europe/Madrid. Upcoming discovery returns only releases with an exact day unless includeApproximateDates=true also admits month, quarter, year, and unknown (TBA) precision; the precision choice composes with the window and both filter dimensions, and the facets reflect it. Empty, review-required, imprecise-date, TBA, and fallback-cover results are valid states. PostgreSQL groups by game, applies filters, distinct facet discovery, presented-release selection, total ordering, count, limit, and offset before any release page reaches the application.

query Parameters
view
required
string (ReleaseView)
Enum: "recent" "upcoming"
Example: view=upcoming
weeks
integer
Default: 1
Enum: 1 2 4
Example: weeks=2

Fixed browsing horizon in weeks; defaults to one week for both views. The response reports the evaluated inclusive dates.

includeApproximateDates
boolean
Default: false
Example: includeApproximateDates=true

Upcoming-only opt-in. Omitted or false, view=upcoming returns only releases with an exact day (day precision). true also returns month, quarter, year, and unknown (TBA) precision releases; each keeps its real precision and follows exact days in the upcoming order. Recent discovery is unchanged and always includes known partial periods that have ended, so true combined with view=recent yields 422 FILTER_INVALID.

platformIds
Array of strings (PlatformId) unique [ items [ 1 .. 100 ] characters ]
Example: platformIds=platform_ps5&platformIds=platform_switch

Repeatable multi-select platform filter (platformIds=a&platformIds=b). Values in this dimension combine with OR; the platform and region dimensions combine with AND. Omit it for no platform filter. Values are trimmed and de-duplicated; an unknown value yields 422.

regionIds
Array of strings (RegionId) unique [ items [ 1 .. 100 ] characters ]
Example: regionIds=region_europe&regionIds=region_worldwide

Repeatable multi-select region filter (regionIds=a&regionIds=b). Values in this dimension combine with OR; the platform and region dimensions combine with AND. Omit it for no region filter, which is distinct from selecting the concrete Worldwide region. Values are trimmed and de-duplicated; an unknown value yields 422.

page
integer >= 1
Default: 1
Example: page=1

One-based page; a page beyond the last returns an empty page.

Featured releases

Public automatic selection of a calendar week's or month's featured releases.

Read the automatic featured releases of one calendar week or month

Reads the automatic selection of one calendar period from the last valid local catalogue: an ISO 8601 week, Monday to Sunday, or a calendar month. Candidates are the games with a qualifying commercial release inside the period: its known date period lies entirely inside it (an exact day of the period, or, for a month, month precision equal to the month) and it is neither cancelled, delayed, nor pending review. A week therefore only ever holds day-precision releases; a month, quarter, year or unknown date is never assigned to a week. Only Full Release participates. A candidate must be an accepted import type, not an edition, with its own known first release in this period and positive locally stored IGDB Hypes. Candidates rank by Hypes descending, then gameId ascending. A game without a usable popularity signal stays a normal catalogue and discovery result but is not ranked, and no popularity value is ever invented. The first item is the period's featured release and up to five more follow; fewer items are returned rather than filling slots. Popularity measures provider-observed attention, never quality, a rating, or an editorial recommendation, and the signal value itself is not exposed. The application derives the evaluation date, the current week and the current month in Europe/Madrid. Without parameters the current calendar month is served. Any period inside the navigation bounds may be selected; it is ranked with the same current local popularity evidence, because no popularity history is kept. Weeks reach 16 weeks before and after the current week. Months reach 10 calendar months back, across years, and forward to the last calendar month lying entirely inside the configured forward horizon of catalogue acquisition; the bound states what acquisition is configured to cover, never that the local catalogue is complete. navigation names the adjacent periods inside these bounds. PostgreSQL selects the qualifying releases, ranks and limits the games, and presents at most one release per platform before anything reaches the application. Each item also carries the landscape context-selected image and optional decorative secondary-card logo, chosen from locally stored provider media metadata and delivered as approved direct CDN references (ADR-0001). Up to two product-owned localized genres accompany each item; only the first item carries the existing localized summary representation. All content is served from PostgreSQL; no provider or translator is called.

query Parameters
granularity
string (FeaturedGranularity)
Enum: "week" "month"
Example: granularity=week

Period granularity. Omitted, it is week when week is present and month otherwise, so a request without parameters keeps serving the current calendar month. Without a period parameter of its own, it selects the current week or month in Europe/Madrid. Combining it with the other granularity's period parameter yields 422 FILTER_INVALID for that parameter.

week
string (IsoWeek) ^(?!0000)[0-9]{4}-W(0[1-9]|[1-4][0-9]|5[0-3])...
Examples: week=2026-W42

ISO 8601 week to feature as YYYY-Www, Monday to Sunday; YYYY is the week-based year, so 2026-W53 runs from 28 December 2026 to 3 January 2027. It must lie within 16 weeks before or after the current week in Europe/Madrid. A malformed week, week 53 of a year with 52 weeks, a week outside the bounds, or a week combined with month or granularity=month yields 422 FILTER_INVALID for /query/week.

month
string (CalendarMonth) ^(?!0000)[0-9]{4}-(0[1-9]|1[0-2])$
Examples: month=2026-10

Calendar month to feature as YYYY-MM. It must lie between 10 calendar months before the current month in Europe/Madrid, across years, and the last calendar month lying entirely inside the configured forward acquisition horizon; the current month is always accepted. A malformed month, a month outside the bounds, or a month combined with granularity=week yields 422 FILTER_INVALID for /query/month.

Catalogue

Public reads from the bounded local catalogue.

Search the bounded catalogue

Searches canonical titles and approved aliases after trimming. Matching is case- and diacritic-insensitive, requires every token, and is non-fuzzy. It never calls a provider. Zero and multiple matches are valid outcomes. Each result carries a bounded releaseContext sample and a separate releaseSummary computed from every locally stored release of that game, plus the scores of only the returned page's games, read from local state after matching, ranking and paging.

Abandon the identified run when its worker no longer proves it is alive

Requires an authenticated session holding the catalogue operator authority and its session-bound CSRF token. An exceptional recovery for a run whose worker has stopped giving heartbeats, for example after the application stopped mid-run: the run named by runId is abandoned only while it still holds synchronization ownership and its last heartbeat is older than the configured abandonment period, the same evidence that reports it stalled and that lets the next run start take its ownership over. That check and the abandonment are one database statement serialized with the worker's own heartbeats, so a worker that proves it is alive meanwhile keeps its run.

Abandonment fences the run: from that moment its worker, if it resumes, cannot commit another Game, record coverage or finish the run, and it gives up at its next safe point. Games it already committed stay committed; nothing is rolled back. The run is answered at once as finished with result abandoned and outcome code SYNCHRONIZATION_ABANDONED_BY_OPERATOR, distinct from SYNCHRONIZATION_ABANDONED, which a later run start records, and ownership is free for the next run. Nothing is retried and recurring schedules do not change.

A run whose heartbeat is within the abandonment period is 409 SYNCHRONIZATION_RUN_NOT_STALE: request its stop instead. A finished run, including one already abandoned, is 409 SYNCHRONIZATION_RUN_FINISHED, and a run that history does not hold is 404 SYNCHRONIZATION_RUN_NOT_FOUND; none of them changes anything.

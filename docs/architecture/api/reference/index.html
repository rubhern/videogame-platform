Browser-facing API for the approved learning MVP vertical slice.

Provider-independent, same-origin contract for release discovery, a month's release calendar, weekly and monthly featured releases, the player-rating game ranking, bounded-catalogue search, public game details, the selectable platform taxonomy, BFF session discovery, the authenticated user's ratings, rating statistics and preferred platforms, and the catalogue operator's synchronization status, coverage, bounded and historical synchronization requests and the stop or abandonment of one run. It contains only the twenty-five approved method/path operations.

Authentication navigation under /auth and the management-port synchronization, repair and localization commands are separate BFF and operational boundaries and are intentionally not exposed here. Provider image binaries are loaded from an approved CDN reference or replaced by a product-owned fallback; this API does not copy, proxy, or redistribute them.

Historical synchronization

Operator-controlled durable calendar-month backfill.

Read durable historical synchronization progress

Operator-only, local durable evidence. Commands require session-bound CSRF proof. Calendar months are processed sequentially through ordinary reconciliation; first and last months are clipped to the inclusive requested dates (1950 through 2099). Completed months include deliberately skipped covered months. Completion does not imply error-free acquisition of every Game. Empty completed months are checkpointed. Counters total completed attempts only, excluding skipped months and failed attempts; they count processing, not distinct catalogue identities across months. A new target cannot replace unfinished work. Resume is explicit, including after restart. No startup action resumes provider work. Scheduled runs take priority between months. Read status after an ambiguous command before repeating it. No completion estimate.

Releases

Public release exploration over an inclusive date range.

Explore the releases of an inclusive date range grouped by game

Reads a bounded page of games from the last valid local catalogue publication whose releases fall in an inclusive date range. Without from and to, the range is the current calendar week, Monday to Sunday, derived by the application in Europe/Madrid; the response states the evaluation date and the evaluated range. Each game appears once with only the releases that match the range and active filters, presenting at most one of them per platform (see ReleaseItem); page.totalItems counts games, not releases.

Days up to and including the evaluation date hold what has happened: a release with an exact day inside the range, or with a month, quarter or year period that has ended and overlaps the range, neither cancelled nor delayed. Later days hold what is expected: a release with an exact day inside the range that is not cancelled. A month, quarter or year period that has not ended joins, not cancelled, only with includeApproximateDates=true and only when it overlaps the range from the evaluation date on. A release with an unknown (TBA) date never belongs to a range. No release receives an invented day, and each keeps its real precision.

Platform and region filters are multi-select: values within one dimension combine with OR and the two dimensions combine with AND. availableFilters is contextual and faceted: platform options reflect the current range and the active region selection (never restricted by the active platform set), region options reflect the current range and the active platform selection (never restricted by the active region set), and a currently selected valid value always stays representable. sort orders the games before pagination, by date, Hype, community score or external player score; every order reads local state only and never calls a provider. Empty, review-required, imprecise-date and fallback-cover results are valid states. PostgreSQL groups by game, applies the range and filters, distinct facet discovery, presented-release selection, total ordering, count, limit, and offset before any release page reaches the application.

Since 4.0.0, from, to and sort replace the view and weeks parameters, which are now unknown parameters, and the response no longer carries view. Migration: a former recent window is to = today with from 7 × weeks − 1 days earlier, a former upcoming window runs from today; the order is now one ascending date order whatever the range.

sort
string (ReleaseSort)
Default: "releaseDate"
Enum: "releaseDate" "hype" "rating" "externalPlayerScore"
Example: sort=hype

The order of the games, applied before pagination; every order ends in the unique gameId. releaseDate is ascending by each game's first presented release: the last day of its known period (the day itself for an exact date), an exact day before a month, quarter or year period ending the same day, then the case-insensitive canonical title. hype puts the highest locally stored IGDB Hypes first, the popularity signal Destacados ranks with, whose value is never exposed. rating puts the highest Gameómetro community mean, at the one decimal shown, first, then the larger number of ratings. externalPlayerScore puts the highest locally stored external player score (currently IGDB players), at the one decimal of its /10 ExternalPlayerScore value, first, then the larger number of that source's ratings. A game without the chosen signal follows every game with one and is never treated as zero; ties continue with the releaseDate order.

Release calendar

Public per-day release counts of one calendar month, from the current month on.

Count highlighted games releasing on each day of one calendar month

Reads, from the last valid local catalogue publication, how many games release on each day of one calendar month, for a monthly calendar. Without month the current month in Europe/Madrid is served. Navigation never goes back: a month must lie between the current month and the last calendar month lying entirely inside the configured forward acquisition horizon, the same forward bound featured months use; the current month is always accepted. The bound states what acquisition is configured to cover, never that the local catalogue is complete.

This is the highlights calendar: only games with locally stored IGDB Hypes >= 10 qualify; missing or lower Hype is excluded. The threshold is fixed, not a percentile recomputed per request. It filters contextual facets as well as day counts.

The calendar is active from the evaluation date on: days of the month before it are never counted. A day holds only releases with that exact day, under the release explorer's own rules (GET /releases): never cancelled, and on the evaluation date not delayed either. days lists each day from the evaluation date (or the month's first day, for a later month) to the month's last day holding at least one such release that matches the active filters, in ascending order; a day without one is absent. totalHype is the sum of local Hypes of the qualifying games on that day, counting each game once regardless of how many matching platforms or regions it has. The sum uses the same active filters as gameCount and excludes games below the highlights threshold. gameCount counts games, not releases: a game releasing on several platforms or regions that day counts once. The full explorer lists every qualifying release of that day without a highlights restriction, so its page.totalItems may exceed the calendar's gameCount. The calendar preview reads the leading games from GET /releases with sort=hype and a page size capped by both three and the day's highlighted-game count.

A release known only to its month, quarter or year, or with an unknown (TBA) date, never belongs to a day and is not counted; nothing is attributed to an invented day or month.

Platform and region filters, activeFilters and the contextual, faceted availableFilters follow GET /releases, evaluated over every release the calendar counts. PostgreSQL applies the filters, groups and counts; the response holds at most 31 days, and no game page is read. No provider is called, and the representation never varies on a session.

Featured releases

Public automatic selection of a calendar week's or month's featured releases.

Read the automatic featured releases of one calendar week or month

Reads the automatic selection of one calendar period from the last valid local catalogue: an ISO 8601 week, Monday to Sunday, or a calendar month. Candidates are the games with a qualifying commercial release inside the period: its known date period lies entirely inside it (an exact day of the period, or, for a month, month precision equal to the month) and it is neither cancelled, delayed, nor pending review. A week therefore only ever holds day-precision releases; a month, quarter, year or unknown date is never assigned to a week. Only Full Release participates. A candidate must be an accepted import type, not an edition, with its own known first release in this period and positive locally stored IGDB Hypes. Candidates rank by Hypes descending, then gameId ascending. A game without a usable popularity signal stays a normal catalogue and discovery result but is not ranked, and no popularity value is ever invented. The first item is the period's featured release and up to five more follow; fewer items are returned rather than filling slots. Popularity measures provider-observed attention, never quality, a rating, or an editorial recommendation, and the signal value itself is not exposed. The application derives the evaluation date, the current week and the current month in Europe/Madrid. Without parameters the current calendar month is served. Any period inside the navigation bounds may be selected; it is ranked with the same current local popularity evidence, because no popularity history is kept. Weeks reach 16 weeks before and after the current week. Months reach 10 calendar months back, across years, and forward to the last calendar month lying entirely inside the configured forward horizon of catalogue acquisition; the bound states what acquisition is configured to cover, never that the local catalogue is complete. navigation names the adjacent periods inside these bounds. PostgreSQL selects the qualifying releases, ranks and limits the games, and presents at most one release per platform before anything reaches the application. Each item also carries the landscape context-selected image and optional decorative secondary-card logo, chosen from locally stored provider media metadata and delivered as approved direct CDN references (ADR-0001). Up to two product-owned localized genres accompany each item; only the first item carries the existing localized summary representation. All content is served from PostgreSQL; no provider or translator is called.

Since 4.1.0, platformIds restricts the candidates before they are ranked: only a qualifying release on one of the named platforms makes its game a candidate, and each item presents only those releases. The ranking, its limit and its tie-breaker are unchanged, so a restricted selection is the ranking of the restricted candidates, never a filtered copy of the unrestricted six. The selection states no_qualifying_releases when none of the named platforms has a qualifying release in the period. Without platformIds the selection is unchanged. The representation depends only on the request's explicit parameters, never on a session.

Read personal rating statistics

UC-015. One repeatable-read snapshot of only the authenticated principal's current active ratings and Ratings-owned projected local genre/game context. No query inputs, external/community scores or provider access. Fixed-size aggregates, never a full history. Each rated game contributes its one personal contribution: the direct score, or the unrounded mean of its scored platforms. All means use the unrounded contributions and round half up to one decimal only for presentation. The distribution places each game once, in the bucket of its contribution rounded half up to the nearest integer (8.5 counts as 9), so bucket counts sum to the total while the mean stays exact. A genre receives one full contribution for every rated game assigned to it, so genre counts overlap; games without genres are counted separately. Genre lists hold at most six entries: most rated by count descending then genreId ascending; best rated (at least three games) by unrounded mean descending, count descending then genreId ascending. Extremes compare unrounded contributions; ties select gameId ascending and count every game with exactly that contribution. Activity is twelve calendar months ending in evaluatedOn's month in Europe/Madrid, counting surviving ratings by original creation time; edits do not move a contribution and deletion removes it. It is not a historical score or playing log. Platforms read only the played platforms the user recorded on current ratings, never Catalogue releases, preferred platforms or devices; see PersonalPlatformInsights.
